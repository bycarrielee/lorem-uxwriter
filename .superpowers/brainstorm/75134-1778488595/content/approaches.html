Three architectural approaches

How should the system handle the relationship between the copy library and the AI?

A

Structured lookup → AI (Recommended)

Library search is a deterministic database query before the AI is invoked. The AI only fills gaps the library doesn't cover. Source is always explicit: library hit, adapted, or AI-generated.

Flow: User submits copy → DB query for matching patterns → match found? surface it → no match? Claude API reviews against foundations + patterns → structured output
✓ Deterministic library matching
✓ Clear source transparency
✓ API-ready from day one
✗ More upfront DB work
Stack: Next.js · PostgreSQL · Claude API
B

RAG (AI-first with semantic search)

Copy library is embedded as vectors. Everything goes through the AI — it semantically retrieves relevant library entries as context before responding. More flexible matching.

Flow: User submits copy → vector similarity search retrieves relevant library entries → Claude API receives copy + retrieved context → structured output
✓ Fuzzy/semantic matching
✓ Scales well with large libraries
✗ Less deterministic
✗ Harder to explain source clearly
✗ Extra infra (vector DB)
Stack: Next.js · PostgreSQL + pgvector · Claude API
C

File-based (lightweight, no DB)

Content system lives in structured JSON/Markdown files. The AI loads relevant files on demand. No database needed initially — faster to build, easier to edit directly.

Flow: User submits copy → file system lookup (JSON pattern files) → relevant files loaded into context → Claude API reviews → structured output
✓ Fastest to build
✓ Human-editable content
✗ Not API-ready
✗ Doesn't scale beyond ~500 entries
✗ Needs migration later anyway
Stack: Next.js · File system · Claude API
